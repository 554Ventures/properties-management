- [x] **Persist askUserQuestion selections** *[x] shipped 2026-08-03*: the shared `AskUserQuestionBlock` had no field recording the chosen option — the selection lived only in client state, so any transcript re-read rendered the question unanswered. As-built: optional `answeredOptionIds` + `answeredFreeText` on the block schema (additive), stamped onto the persisted block by `resumeTurn` — exactly once, since only the `/answer` claim winner reaches it (rides the atomic `awaiting_user→running` transition) — and written again by every subsequent blocksJson persist. Covered by API round-trip/race/free-text tests and component tests; verified end-to-end in the dev app (answer → server block carries the ids → UI renders answered from server data on the post-stream refetch).

- [x] **Atomic session-state transitions** *[x] shipped 2026-08-03*: the chat 409 guards were read-then-act (`chat.service.ts`) — two concurrent sends (or answers) could both enter the agent loop, duplicating model turns and message rows. As-built: both turn starts are now conditional `updateMany` claims in `chat.service` — send claims `idle→running` (stamping the first-message title in the same write), answer claims `awaiting_user→running` while consuming the paused provider state (context kept) in the same write; a loser matches 0 rows and 409s *before* the SSE hijack, so it still gets a JSON error. The agent-loop entry points no longer write status on entry (a send-setup failure releases the claim back to `idle`); the in-loop pause/finalize writes are unchanged since only the running turn owns the session while `running`. Check-then-create review done with it: rent materialization retries on P2002, `recordPayment`/`confirmWithRentLink` re-read inside their `$transaction`, contractor adoption is an idempotent `updateMany` — no other read-then-act state machines found. Race tests: concurrent double-send and double-answer each assert exactly one 200 + one 409 and unduplicated messages.
- [x] **MCP per-client OAuth** (PRD §10) *[x] shipped 2026-08-09*: the MCP registry is now reachable remotely at `POST /mcp` (stateless Streamable HTTP, root-mounted — the Claude Desktop connector URL), authorized by Supabase's OAuth 2.1 server. As-built: RFC 9728 protected-resource metadata at `/.well-known/oauth-protected-resource[/mcp]` advertised via `WWW-Authenticate` on `/mcp` 401s; Claude self-registers through Supabase's dynamic client registration; consent is rendered by our own `/oauth/consent` page (Supabase hosts none), and Settings → **Connected AI clients** lists/revokes grants via `supabase.auth.oauth.listGrants`/`revokeGrant`. **The `Integration`/`scopesJson` design was deliberately not used**: Supabase's scope list is fixed (`openid profile email phone offline_access`) with no custom scopes, so per-client scopes are unachievable at the OAuth layer. Write authority instead comes from the acting user's own role/permissions through the existing `deniedWriteTools(role, permissions)` — a member can't reach a write through an AI client that their REST route would refuse. Hardening: tokens bearing a `client_id` claim (Supabase stamps these only on third-party grants) are accepted on `/mcp` and rejected everywhere else, so an open-DCR token is never a general REST credential. `HEARTH_MCP_ENABLE_WRITE` survives as the stdio-only gate. Covered by `mcp-http.test.ts` (real Streamable-HTTP client against a listening server) + `OAuthConsent.test.tsx`/`ConnectedClients.test.tsx`.

Covered by `lease-tools.test.ts` + the `mcp.test.ts` write-gating list. - [x] **Audit coverage completion**: property/unit/tenant/lease CRUD is now audited (create/update/archive/restore/terminate/renew/add_tenant/remove_tenant) alongside transactions, payments, reminders, reports, insights.
- [x] **Transaction-delete / RentPayment desync**: deleting a rent-linked ledger Transaction is now blocked with a 400 in `transaction.service.remove` (SetNull remains the DB-level fallback for writes that bypass the service).
- [x] **Session hygiene** *[x] shipped 2026-08-05*: sessions left `awaiting_user` were never expired server-side. As-built: `chat.service.expireStaleSessions`, run by the daily jobs (in-process tick + CF cron endpoint) — an `awaiting_user` session past **7 days** reopens as idle with the paused resume state dropped (screen context kept; the unanswered question block stays in the transcript and renders frozen; sends work again instead of 409ing forever), and a `running` session past **1 hour** is a zombie claim from a crash between the atomic claim and finalize, released back to idle untouched. Each flip is a conditional `updateMany` keyed on current status, so a sweep racing a genuine answer/turn loses cleanly. The generous awaiting TTL is deliberate: with session restore shipped, "answer it days later" is a real flow. Counters (`chatSessionsExpired`/`chatSessionsReleased`) ride the `DailyJobsResult`.
